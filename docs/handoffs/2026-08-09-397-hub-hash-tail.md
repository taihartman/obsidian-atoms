The bug: on a **non-force** Ask mirror sync, the hub planner's stale copy of the hash map overwrote
the atom planner's freshened entries, so every dirty atom's *old* hash got persisted. The next pass
saw it dirty again and re-uploaded it — forever. Invisible from the UI, which reported a healthy
"last pushed" either way. Present since #225 on 2026-08-01. Costs bandwidth, Plus request volume,
and Anthropic spend (re-upload re-fires the expand path).

## Decisions & constraints

Settled — **do not relitigate**:

- **Both fixes suggested in issue #397 are wrong.** Reversing the spread to
  `{ ...hubNext, ...atomNext }` is symmetric: `atomNext` carries stale *hub* entries and would
  clobber freshened hub hashes instead. Seeding the hub planner from `{}` breaks the line-394 skip
  check, so every hub re-uploads every pass. The bug moves rather than dies. The landed fix avoids
  both.
- **`planAskMirrorUpsert`'s return contract stays as-is.** Direct unit tests at
  `test/askMirror.test.ts:84` and `:293` pass `first.nextHashes` back in and rely on it being a full
  map. Changing it to return deltas would break them and widen the blast radius. The fix is at the
  merge site instead.
- **The guard is `if (h)`, not a non-null assertion.** `noUncheckedIndexedAccess` makes the lookup
  `string | undefined`; the honest guard costs two lines and keeps `tsc` clean.
- **#397 is unrelated to #372.** It was found incidentally during that merge review. Do not fold
  them together.

Hard constraints:

- **Never run `npm test` or `npm run build:www`.** `pretest` runs `build:www`, which deletes the
  tracked fixture `docs/field-notes/published/2026-08-01-sample-loop.json` (#343). Use
  `npx vitest run` and `npx tsc --noEmit`. `npm run build` alone **is** safe — it is
