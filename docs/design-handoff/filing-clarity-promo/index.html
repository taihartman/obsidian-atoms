Filing clarity & promo code

A first-week user cannot tell what Who does the filing is asking them, and nobody holding a promo code can find where to spend it. Revised after an Apple read: the row stops asking a question, the two options stop being peers, and three promo entries collapse to one.

What changed in v2. The row becomes a noun with state on the right, the way every iOS Settings row works. Atoms Plus goes first and your own key goes second, because a recommended path and an escape hatch are never peers. Promo becomes one permanent Redeem code row where the money lives. Two things Apple would do were refused, both for the same reason: this product's honesty is not decoration.

Already shipped, just buried. Settings → Account → email → Use promo code opens Stripe Checkout, and the server already sends allow_promotion_codes: "true". Nothing to build on the billing side. Stripe owns the code field, so the plugin never renders one.

The Apple read

Four moves. Two taken, two refused. The refusals matter more than the adoptions: they are where this product is deliberately not Apple.

Taken

A row is a noun, not a question

iOS Settings rows never ask anything. Wi-Fi › Home. Screen Time › On. The row names the thing; the value says where it stands. All three names we debated were questions. The word "filing" gets defined once, in the group footer, which is exactly the job group footers already do.

Taken

Demote, do not balance

Apple never puts a recommended path and an escape hatch side by side. Plus becomes the screen; your own key becomes a second, quieter group underneath. This is what removes all eight terms from the decision instead of seven.

Adjusted after checking the code. The purer iOS shape is an unheadered first group, but SettingGroupSpec.header is a required string, and widening it means touching the primitive every group on the tab renders through. Recommended is the better answer anyway: for this reader, being told which one to pick is the most useful sentence on the screen.

Refused

Silence about the vendor

Apple would delete "runs on AI built by a company called Anthropic, and it costs a few cents every time." The vendor and the unit economics are the vendor's problem. But pillar three of this product is the honest middle, and consent to send is gated on saying what gets sent. Reticence is the one thing here that cannot be borrowed.

Refused

Privacy behind a link

Apple's placement is a standard secondary sheet: About Siri & Privacy. Tempting. But What gets sent previews a versioned, acknowledged disclosure, and moving a consent surface behind a link to win a layout argument is how a device ends up filing under a grant nobody read. The three lines stay inline.

The row stops asking

Filing plus a state, in every account condition. Shorter than all three names we debated, and it teaches the word through the value rather than the label. The definition moves into the File group footer, where the word first appears.

Plus first, your own key second

Pick one is gone. Two peers become a recommendation and an alternative, and the credential form leaves the decision entirely. Every one of the eight terms now renders in front of the person who chose to deal with it, and nothing is deleted.

One permanent Redeem code

Apple's Redeem Gift Card or Code is instructive for what it is not: not conditional, not near the feature, not a question. Three rows and three action ids collapse to one row and one id, in the Plus group, where the money lives — plus a copy of it at the bottom of the main screen, next to an Account row that does not exist there yet.

Where Apple's pattern does not survive Stripe. Apple's redeem row is unconditional because a code credits an account balance. Atoms has no balance: a code applies to a subscription. What that means state by state is the next section, and it is where this design had a hole. Also: Apple's redeem sheet offers Use Camera, because typing codes is miserable. Stripe owns the field, so that is off the table. A real cost of the constraint, not a free win.

"Signed in" is six states, and one of them was a dead end

deriveAccountState returns six kinds. The first draft said the row hides on "a live subscription", which quietly took it away from the person most likely to be holding a code: somebody three days into a fourteen-day trial.

The scope question this opens. Routing a live subscription to the portal needs the promotion-code option enabled in the Stripe portal configuration. createPortalSession (stripe.mjs:308-312) sends no configuration param, so we are on the Dashboard default, and two earlier plans put that toggle explicitly out of scope. Turning it on is ops, not code, and it has to be verified in the Dashboard before this route can be promised. Second caveat: portalHasSubject (settings.ts:2467) gates the portal on a real Stripe customer, so an account minted without one still has no route and must say so rather than offering a button that fails.

Your calls

Two settled by the Apple read. One new one, and it is the biggest: the trial case adds a live-Stripe dependency to a plan that had none.

1 · The portal route for a live subscription

In scope, or out? In: a trialing user with a code has a route, but the plan gains a Stripe Dashboard dependency that has to be verified before it can be promised. Out: ship Redeem for the four states with no subscription, and have active say plainly that a code cannot be added from here yet. Recommendation: in. A hidden row is worse than a dead end, because it is an invisible one.

2 · Split the key screen

Still the only structural change, and the only reason this is a full-lane job. Moving the key field, the fallback toggle and the naming rule behind Use your own Anthropic key is what clears the decision screen. Yes or no?

3 · "We pay for the AI"

Plain, and possibly too plain. The alternative is Apple's own word: Included. Settled by the atoms-voice skill unless you rule first.

Settled
